What this is

A working mini-ERP for Wasatch Board Co., a fictional Utah skateboard company, built for GSCM 401. The company sells 20 parts and assembles 5 complete boards at its Orem warehouse, and sells from two stores (Provo and Salt Lake City). Customers can also order online for store pickup, including a custom board they design.

The database holds twelve months of generated business history (16 Nov 2025 to yesterday) plus anything typed in since, so every report has real-looking data behind it.

The rules everything follows

  • One inventory ledger. Every stock change (sale, receipt, transfer, build, return, count) is one row in a single movements table, with a + or − quantity and the cost at that moment. On-hand is the sum of that ledger. Rows are never edited or deleted; a mistake is fixed with a new correcting row. Stock can never go below zero.
  • Everything is calculated. No total, cost, status or metric is typed in. Each screen recalculates from the stored transactions, so changing an input (a setting, a sale, a receipt) changes every result that depends on it.
  • Weighted average cost. Each item has one average cost for the whole company. When stock arrives (purchase receipt, finished boards, restocked return): new average = (units on hand × old average + units in × their cost) ÷ (units on hand + units in). A complete board's cost is the cost of the parts actually used to build it.
  • All or nothing. Each business transaction (a sale, a receipt, a build, a return) runs as one database function. If any part fails, for example not enough stock, nothing is saved.

The formulas

  • Usage: units sold + units used in production, averaged per day over the last 90 days (d). σ is the standard deviation of that daily usage.
  • Reorder point = d × L + z × σ × √L, where L is the supplier's lead time in days and z = 1.65 (the service level).
  • EOQ = √(2DS ÷ H), where D = the last 365 days of usage, S = $25 per order, and H = 25% of the item's unit cost per year.
  • Periodic review: each item has a review interval (30 days by default). Due for Review lists items past their date; ordering or marking an item reviewed moves the date forward.
  • MRP: boards first. Gross need = sales forecast + open sales orders; net = gross − boards on hand − open production orders. Boards to build × the bill of materials = the parts needed that week, plus part sales and custom builds. Net parts = need − parts on hand − open purchase orders. Order by = the week's start − the supplier's lead time.
  • P&L: revenue − refunds = net sales; − cost of goods sold (less cost returned) = gross profit; − production scrap − returned goods written off − stock count losses = profit. Sales tax is collected for the state, so it is not revenue.
  • Inventory turnover = cost of goods sold ÷ average inventory value over the same period.
  • Production: final yield = good ÷ started; first-pass yield = (good − reworked) ÷ started; scrap rate = scrapped ÷ started; build time = finish − start.
  • Supplier score (0–100) = 40% on-time rate + 40% fill score + 20% lead-time score. A (90+) = Keep, B or C (70–89) = Watch, D or F (below 70) = Replace.

The numbers in this section are read from the Settings page, so they always show the values in use.

Security and multiple users

  • Everyone signs in with an email and password. Staff logins see the ERP; customer logins see only the shop.
  • The database itself enforces this (row-level security), not just the web pages. A customer can never read costs, other customers' orders or staff screens, even by changing the web address.
  • Changes are broadcast in real time: when one person sells, receives or builds, every other open screen refreshes.

Simplifications we chose

  • No accounting ledger: the P&L is calculated from sales, returns, production and stock records. No operating expenses (rent, wages).
  • Transfers between locations arrive immediately. Customers pay at pickup; payment is not recorded.
  • Stock is not reserved for open orders; it is taken when the order is fulfilled.
  • MRP plans each week exactly what is short (lot-for-lot), without safety stock.
  • The year of history is generated by a script with realistic seasonality, events and supplier behaviour, written through the same ledger as live transactions.

How it was built

  • AI tools: the code and database design were written with Claude Code (Anthropic), directed and reviewed by the team from a written specification.
  • Database, logins and realtime: Supabase (a hosted PostgreSQL database).
  • Front end: plain HTML, CSS and JavaScript with no framework and no build step.
  • Hosting: GitHub Pages, from a public GitHub repository.
